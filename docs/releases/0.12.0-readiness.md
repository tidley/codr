### Demonstrated linker/startup defect and bounded fix

The dependency-free [musl startup fixture](../../tests/fixtures/musl_startup/README.md)
reproduces the defect without Codr, Tokio, OpenSSL or Odin. Rust 1.97.1 selects
static PIE for x86_64 musl. The native musl GCC specs inject
`-dynamic-linker /lib/ld-musl-x86_64.so.1` without suppressing it for
`-static-pie`. The resulting ELF has type `DYN`, no `DT_NEEDED` libraries, but an
`INTERP` segment. Loading that self-relocating executable with the musl loader
segfaults before it prints anything. Without the loader installed, execution
instead fails with `ENOENT` even though the executable itself exists.

The local red/green experiment used Rust `1.97.1 (8bab26f4f)` and GCC `12.2.0` with
musl 1.2.3-1 packages extracted from Debian's configured package repository into
centrally allocated fastbuild scratch storage. Only the extracted specs' paths
were adjusted; no system packages, loader symlinks or machine configuration were
installed or changed. This is not the Ubuntu 22.04 CI container. Because this
machine has no installed musl loader, the red executable was invoked through the
extracted loader explicitly; it returned `-11` (shell-equivalent 139), with no
stdout. The green executable ran directly and printed `musl startup passed`,
returning zero. Both were PIE (`DYN`) with no `DT_NEEDED`; only the red build had
`INTERP`. Cargo's reported output was under
`/mnt/fastbuild/cargo/musl_startup-415bbfc18ab7e8fb/`.
The retained fixture executable SHA-256 values are:

- red: `caedc12176826e168c631275f58df7ebfb1391c5f38e784606fcebc018aae994`
- green: `7ca3ba2b065084994ed9d6bf77e2c84018c20a5e0867d0b19bb5ea0f9eccacb2`

The repair adds only the target-specific linker argument
`-C link-arg=-Wl,--no-dynamic-linker` for x86_64 musl in both release and preview
jobs. It retains the musl math linker, PIE, self-relocating CRT, native Odin
flags, all source/security/storage pins and every existing package smoke. It
does not switch to non-PIE executables, increase stack limits or bypass startup.
ARM64 and Darwin flags are unchanged. The Python packaging regression failed on
the missing argument before the workflow edit and all six focused packaging
tests passed afterward. The four focused `test_release.py` tests also passed.
These are local regression results, not platform package approval.

The unchanged application also built locally for GNU Linux in release mode

With an isolated home and explicit missing config, `--version` and `--help`

`fc7a3651657127f21dc8852a5cd89ded225f1eab1b826b56717d67bba75600b8`.

- `repos/tidley/codr/actions/jobs/133603675122/logs`: final link used `cc` with
  Rust's `x86_64-unknown-linux-musl` CRT and glibc's

  and failed with the same two undefined symbols; Cargo exited 101.

MDK Markdown adds `-lm` to the final link. Selecting the host GNU linker driver
mixed glibc's math archive with musl. Both Linux jobs already install
`musl-tools`; explicitly selecting its native `musl-gcc` wrapper for each musl
target is the minimal repair. Target-specific Cargo environment variables leave
Darwin and the standalone GNU compatibility connector unchanged. Static-loader,
version/help, connector protocol/provenance and upstream policy gates remain.
