### Recovery limits: immutable source versus repaired workflow

The existing workflow supports `workflow_dispatch` with `source_ref`, and
`linux_preview: false` retains host checks and all four package lanes. A dispatch
using a repaired workflow and a full repaired source SHA can verify/package that
new source at version 0.12.1, but **cannot publish a stable release**: `release`
requires a tag-push event. Rerunning the failed tag run retains its old workflow
and does not pick up this prerequisite fix. Moving `v0.12.1` is not an option.

A repaired workflow could instead dispatch with the original full tagged source
SHA, retaining the original source identity while changing only build-tool
provisioning. That is a possible same-source verification build, not an existing
stable promotion contract. The repository has no stable artifact-promotion job
or documented same-version contract separating repaired workflow provenance from
tagged application source. The preview publisher is not a stable recovery path
and requires a Linux-only manifest; do not bypass that gate or change channels.

The coordinator must settle the source/version/publication path before another
release attempt: use an explicitly approved exact-tag build/promotion contract
if one is established, or obtain a new-version decision. This worker neither
implements such a contract nor selects a new version. Any proposed reuse must
record the actual workflow and application source, all required gates, build
inputs/signing and downloaded exact-byte SHA-256 evidence. Existing successful
artifacts remain tied to `29a4410` and run `45587845551`, not the repaired SHA;
they have not been downloaded or checksum-verified by this worker. Do not relabel
them, mix source identities, or claim the failed matrix qualified a release.
