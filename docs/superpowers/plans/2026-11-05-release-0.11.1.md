# codr 0.11.1 Release Preparation Plan

**Goal:** Prepare reviewed 0.11.1 source, accurate release documentation and verified four-platform candidate packages without publishing a tag or release.

**Architecture:** Continue in the existing `fix/stale-custom-decision-routing` checkout. Keep the unchanged MDK pin, dependencies, storage cohort and release workflow. GitHub is primary; mirror approved source and existing CI evidence through supported ngit commands without rebuilding for the mirror.

**Tools:** Git SSH signing, Cargo, Python unittest, GitHub CLI, ngit with the `devbox-amber` signer.

## 1. Finalise documentation

- Update `CHANGELOG.md`, `README.md`, `docs/releases/0.11.1.md` and `docs/releases/0.11.1-readiness.md` for the final scope, status punctuation, acceptance limits and current local deployment.
- Preserve original contributor credits from commit authors and verified GitHub/ngit records. Do not attribute baseline work as a new 0.11.1 contribution.
- Keep fresh setup pinned to supported 0.9.0 bootstrap and retain upgrade/account-safety warnings. Exclude Foreman, sharing, recovery and encryption experiments from the separate main checkout.

## 2. Verify and review

Run from the candidate repository using the configured build-storage adapters:

```sh
cargo fmt --all --check
cargo test --locked --tests
cargo clippy --locked --all-targets --all-features -- -D warnings
python3 -B -m unittest discover -s tests -p 'test_*.py' -v
git diff --check
```

- Investigate any failure before changing production code or verification settings. Do not commit temporary test-path configuration.
- Obtain two independent read-only reviews: correctness/contracts/state/security, and tests/regressions/complexity/scope. Resolve demonstrated findings and repeat affected verification.
- Sign the final source commit, then verify it locally with `git verify-commit HEAD` before any push.

## 3. Publish preparation source, not a release

- Push the reviewed branch to the existing GitHub `origin` and update PR #21's scope and verification evidence. Do not merge, tag or publish as part of build preparation.
- Mirror that exact branch to the existing public ngit repository URL using the `devbox-amber` signer. Tom approves signing in Amber. Compare GitHub and mirror ref hashes; report pending signing or failed mirrors explicitly.

## 4. Build the exact candidate once

- Inspect existing runs and retained artifacts first. Reuse a complete matching run instead of launching another.
- Run the unchanged build-only workflow, with the exact signed source commit:

```sh
gh workflow run build.yml --repo tidley/codr \
  --ref fix/stale-custom-decision-routing \
  -f source_ref="$(git rev-parse HEAD)" -f linux_preview=false
```

- Require Linux/macOS checks and all four package lanes: Linux x86_64/aarch64 and macOS x86_64/aarch64. Preserve the run URL, commit, build inputs, platform/signing evidence and artifact expiry.
- Download all four artifacts to the adapter-reported project build storage. Verify each original archive against its original sibling SHA-256 file and check package contents. Do not rewrite checksums, repackage binaries or claim the local installed binary came from this CI run.
- Update PR metadata and retain a separate verification receipt after the run; do not make an evidence-only source commit that falsely moves artifact provenance.

## 5. Handoff for publication

- Report reviewed source, branch/PR, CI packages, installed local version and mirrors separately.
- Tagging/publication remains a separate approval. The unchanged tag workflow rebuilds; manual artifacts cannot currently be promoted. Do not change that workflow to avoid its gates.
- After an authorised release, mirror its exact GitHub assets and checksum files to Blossom, publish matching signed release metadata, and download/verify the mirrors. Do not publish a test release for CI artifacts.
